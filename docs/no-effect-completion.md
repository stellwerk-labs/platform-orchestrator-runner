# Pipeline completion without a mutating claim

A terminal unsuccessful native pipeline can return an optional `no_effect_receipt` through the existing authenticated result callback. It contains protocol version `stellwerk.no-effect/v1`, SHA256 of the original signed command payload and `effect: not_started`. It contains no deployment credential, executable input or plan. DP must match the authenticated target and retained signed command, and use its own immutable captured predecessor before changing effective-state projection.

Completion rereads the command and current terminal progress in 1 SQLite transaction. The event argument selects only ID/revision; its phase and infrastructure flags are not evidence. Stale revisions, missing authority and current unknown outcomes do not produce a completion. The receipt requires absence of every mutating effect claim, including completed task claims, and absence of a permanent local blocking fact. Failed observations retain their existing contract; successful Plans and successful Applies do not receive this failure-only receipt.

`rollout_no_effect_blocks` records that a mutating claim, applying/unknown progress or infrastructure application has ever been recorded. Claim and fact writes share the same transaction; risk progress and its fact likewise commit together. Initial upgrade creates and seeds this indexed table atomically from retained claims and actual progress/history before DBOS recovery. A failed seed rolls back table creation. Later completion reads use indexed facts, not a scan of historical events.

An unknown outcome followed by a failed status cannot become proof that no effect started. A completed no-op Apply also claimed execution and remains ineligible, even with zero resource changes. The fact has no clearing API. Future GC must preserve it alongside command replay/consumption identity across signed-command expiry, receipt retention and backup-quarantine requirements; removing detailed events or artifacts must not resurrect eligibility.

The claim boundary assumes site-controlled approved tools obey their declared execution/retry contract. It is not isolation for malicious customer code or a proof that an arbitrary program made no external change. Uncertain effects still require separate evidence-based reconciliation and retain existing fences.

Deploy the compatible DP receipt consumer and predecessor capture with this Runner change. Old commands lacking captured DP authority remain conservatively ineligible for automatic projection; do not manufacture a receipt, delete claims/facts or clear an unknown fence to bypass that limitation. Actual Gateway delivery, process-kill and backup/restore qualification remain separate from the local SQLite/real-IaC source tests.
