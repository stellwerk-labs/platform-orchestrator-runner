# Retained plans with external providers

The native reviewed-plan failure exposed a general retained-closure limitation: Terraform/OpenTofu initialization uses provider-cache symlinks, while the old archive rejected symlinks and attempted to fit provider binaries into a 2 MiB plan archive. Successful Init, Plan and saved-plan rendering could therefore end in retention failure. The failed Deployment and its diagnostics remain unchanged.

The bounded fix reuses the existing Runner retained-plan implementation only for the site-local/native `NewLocalRunner` constructor. A private constructor marker enables it; no public option or legacy-factory inference is used. Ordinary legacy factory Plan and its existing retained-format behavior remain unchanged.

- Before Plan, installed provider packages are materialized into private work-directory regular files. Their exact file hashes and executable modes are recorded. Only recognized provider package cache links are dereferenced; symlinked parent directories and unsupported file types fail closed.
- The retained encrypted snapshot includes the lockfile and exact provider-file manifest, while omitting `.terraform/providers` binaries. Existing archive, expanded-size, tool-hash, binding, OS and architecture checks remain. Provider materialization is bounded to 64 packages, 4096 files and 1 GiB total copied bytes.
- Provider snapshots use binding schema `stellwerk.retained-plan/v2`. An old Runner's exact binding comparison rejects them before Apply. The new reader accepts existing `v1` snapshots unchanged and refuses a provider manifest hidden in a `v1` snapshot. Newly produced snapshots require provider identity captured by the actual Plan path.
- Restore runs `init -backend=false -get=false -lockfile=readonly`, verifies the selected packages against the retained lockfile, materializes private copies, and requires their complete manifest to match the reviewed identity. It does not generate a new Plan or initialize/migrate state storage. A mirror changed before restore fails; a mirror changed after restore cannot alter the private provider executed by Apply.
- Development overrides, provider reattachment and checksum-bypass cache settings are unsupported for retained plans. Bounded CLI-configuration inspection rejects them before Plan and on restore, including JSON/HCL quoted escaped override keys and case-folded checksum-bypass fields. Selection follows actual supported tool precedence (`TF_CLI_CONFIG_FILE`, then deprecated `TERRAFORM_CONFIG`); `TOFU_CLI_CONFIG_FILE` does not suppress active defaults. Main files, default `.tfrc`/`.tfrc.json` fragments and OpenTofu 1.13 XDG fallbacks are inspected. Inspection is deliberately conservative, so mentioning unsupported settings in comments is also refused. Native configuration files must remain operator-controlled during a run.

Native reviewed execution now reuses the existing saved-Apply preparation callback: restore and provider verification finish before the durable Apply effect claim. Fresh restore refusal is a known failure with no Apply claim or infrastructure effect; uncertainty after a claim or process start keeps the existing unknown-outcome fence.

Existing absolute configuration/module/data-path portability limits are unchanged. Same-OS/architecture/tool execution and the relative compiled closure are qualified here; this is not a claim that arbitrary externally resolved module paths are portable. Provider installation must remain available through the site's configured verified cache/mirror. An air-gapped site needs those packages locally, with no registry fallback in the offline qualification fixture.

The race-enabled actual Terraform/OpenTofu tests use an installed official `hashicorp/local` binary and a temporary filesystem-only mirror. They prove Plan → human approval → Runner restart → saved Apply, one Plan/Apply, override refusal, checksum refusal, private-copy isolation after cache mutation and old snapshot compatibility. They do not mutate the shared installed provider binary or the preserved failed Deployment.
